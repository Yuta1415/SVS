I. System overview

1. What SVS is

SVS is a security scanning service that ingests a Git repository or a .zip archive, runs three deterministic engines against it, and reports a security posture score with per-finding remediation guidance.

An SVS install is five Docker containers on one machine: a PostgreSQL database, a Redis broker, a FastAPI API, a Celery worker, and an nginx-served React frontend. The API accepts a target, the worker clones or unpacks it into a per-scan directory, and that directory is mounted read-only (or read-write, where a tool must write a report) into throwaway sibling scanner containers. Each scanner's findings are normalized into one common shape, written to the database, and scored. The frontend polls until the scan reaches a terminal state, then renders the findings with triage controls and a link to a server-generated PDF.

AspectReality
Intended deploymentOne operator's own laptop. Not a multi-tenant SaaS, despite some UI text inherited from the original spec.
Analysis typeStatic: SAST patterns, secret detection, dependency CVEs. Nothing is executed, fuzzed, or dynamically probed.
AI involvementNone. Every finding comes from a deterministic tool; every score is arithmetic.
AuthenticationRemoved by design. See section I.2.

2. Design posture: no AI, no auth

Two decisions are load-bearing and easy to misread:

  • No authentication. Every request resolves to a single local user row (backend/app/api/deps.py:11). The users table survives only because projects.owner_id has a non-nullable foreign key to it, and because the historical projects and scans created under the old accounts are worth more than a clean schema. The row is created on first use with an unusable password (!) that no endpoint ever checks.
  • No inference. The scoring service is a closed-form arithmetic function of finding counts. Two scans of the same code produce the same score, which is the point: the number can be reproduced from the report instead of trusted.

Concretely, no endpoint checks a token, no ownership filter is applied anywhere in the API, and the frontend renders a small green local pill in the navbar to say so. Every route is annotated Auth: None (single-user local instance) in the in-app API reference, and that is accurate.

3. The thirty-second version

  1. The operator presses Dispatch Security Pipeline with either a Git URL, a zip archive, or the demo target.
  2. The API validates the URL, clones or unpacks the code into /tmp/svs_uploads/scan_<id>, writes a scans row at PENDING, enqueues a Celery task, and returns immediately.
  3. The worker marks the scan RUNNING and runs Semgrep, then Gitleaks, then a dependency audit, each in its own container with a memory cap and a 15-minute timeout.
  4. Each tool's output is normalized into the same finding shape and inserted.
  5. Scoring sums weighted risk points into score = 100 / (1 + risk / 25).
  6. The worker deletes the scan directory, closes the session, and the scan is COMPLETED (or FAILED with the name of the broken scanner).
  7. The dashboard's 2.5-second polling notices, and the report view renders findings, triage buttons, and a link to the server-side PDF.

3. Two contracts that make scanning possible

Two non-obvious arrangements are what let the worker spawn scanner containers at all. Both are commented in the compose file.

3.1 The Docker socket mount

Both the backend and the worker mount /var/run/docker.sock. The scanners are not libraries or subprocesses; they are sibling containers started through the docker Python client (docker.from_env() in engine/scanner.py:19). The worker talks to the host daemon, so every scanner container is a peer of the worker, not a child of it. This is the single largest attack surface in the system and is documented honestly in section XI.2.

3.2 The host bind at /tmp/svs_uploads

This is a host bind, not a named volume, and the reason is mechanical. A scanner container receives volumes=["/tmp/svs_uploads/scan_42:/src"]. If /tmp/svs_uploads were a named volume, the path the worker passes would not resolve to the same real path on the daemon's filesystem, and the mount would be empty. The bind guarantees the worker and every scanner agree on one absolute path. It is also why uploads live under /tmp on the host rather than inside a container filesystem that would be discarded.

III. Request lifecycle: a scan end to end

This is the trace to read when something goes wrong. Every state transition below is a real line of code.

1. Dispatch

The frontend's IngestScanView collects a project name and either a Git URL or a file. Before calling the API it deduplicates projects: it calls GET /projects/ and reuses an existing project with the same name, otherwise POST /projects/ to register one. Every scan is keyed off a project row, and this avoids forking a duplicate project per scan. The demo path is different: POST /scans/demo clones a fixed target and files the result under its own Demo Project row, so no project is created or named by the client.

Three entry routes exist, all rate-limited at 5 scans per hour per user:

  • POST /scans/git — multipart project_id + repo_url
  • POST /scans/upload — multipart project_id + file, must end in .zip
  • POST /scans/demo — no body; clones https://github.com/juice-shop/juice-shop

2. Ingestion

IngestionService (backend/app/engine/ingestion.py) writes the scans row first, at PENDING, so a scan ID exists before any work. Then:

  • Git — validate_repo_url checks the scheme is http/https/ssh/git, requires a netloc, resolves the hostname through getaddrinfo, and rejects any resolved address that is private, loopback, link-local, multicast, or reserved. Then Repo.clone_from(url, path, depth=1). A clone failure deletes the scan row and returns 400.
  • Zip — reads the whole upload into memory and rejects anything over MAX_FILE_SIZE (50 MB), extracts into the scan directory, and on BadZipFile deletes the scan row and returns 400.

The scan directory is <UPLOAD_DIR>/scan_<scan_id>, i.e. /tmp/svs_uploads/scan_42. The scan ID determines the path, which is why the row must exist before extraction.

3. Queue

The router calls run_security_scan.delay(scan.id, project.id) and returns immediately with the scan ID and its PENDING status. The HTTP request is therefore bounded by ingestion time, not scan time. The task is registered as tasks.run_security_scan, bind=True, max_retries=3.

4. Worker execution

run_security_scan (engine/tasks.py) opens its own SQLAlchemy session (it does not share the API's), builds the project path, and calls ScannerService.run_full_scan (engine/scanner.py:25):

  1. If the Docker client cannot be reached, the scan is marked FAILED and returns. This is the "Docker daemon is not available" path.
  2. The scan is set to RUNNING and start_time is recorded.
  3. Three scanners are constructed and run in sequence, not in parallel: Semgrep, then Gitleaks, then the dependency scanner. Sequence matters only for log readability; there is no data dependency between them.
  4. Each scanner's exceptions are caught as ScannerError and collected into a failures list with the tool name and detail. A broken scanner does not abort the remaining ones.
  5. scoring_service.calculate_score(scan_id, db) runs on whatever the surviving scanners found, so partial results are visible rather than discarded.
  6. If any scanner failed, the scan is FAILED and error_detail holds the joined list, truncated to 500 characters. Reporting COMPLETED with a clean score would hide a broken pipeline as a clean repository.
  7. Otherwise COMPLETED.

Any uncaught exception sets FAILED with a Pipeline error: prefix, and the task itself retries up to three times with a 60-second countdown.

5. Termination and cleanup

In the task's finally, the scan directory is removed with shutil.rmtree and the session is closed. This runs on success and on failure, which is why a finished scan leaves no source on disk and why the report view cannot show the offending line afterwards. The Gitleaks report file, which contains matched secrets in cleartext, is additionally deleted by the scanner itself before that.

6. Client polling

The dashboard polls GET /scans/ every 2500 ms while any scan reports status === 'scanning' (the adapter collapses PENDING and RUNNING into scanning). The ingest view polls GET /scans/<id> every 2 s with a 20-minute deadline. Findings are only fetched on demand when a scan is selected, because loading every scan's findings up front would cost one call per scan on a dashboard that only needs counts.

IV. Scan engines

1. Shared container contract: _run_container

All three scanners subclass BaseScanner (backend/app/engine/base_scanner.py) and share one container runner. Its contract is the difference between a scanner that reports findings and one that hangs:

PropertyValue
Executiondetach=True then container.wait(), never detach=False. Several tools exit non-zero on a successful scan; detach=False would raise before the report could be read.
TimeoutDEFAULT_TIMEOUT = 900 (15 min) enforced by the caller's own deadline, not by the SDK. container.wait() raises ReadTimeout when its poll expires with the container still running; the loop re-arms and keeps waiting. On deadline the container is killed and a ScannerError is raised. This exists because a hung scanner used to block wait() forever, leaving the scan stuck on RUNNING and the Celery task wedged with no cleanup.
Memorymem_limit per scanner (512 MB default, 256 MB for Gitleaks).
Networknetwork_disabled defaults to True; only the scanners that need a ruleset or an advisory DB opt out.
Exit codesaccept_exit_codes extends the set that counts as success. Gitleaks and npm audit exit 1 to report findings, so their callers pass (0, 1); without that, the cleanest repo would scan as FAILED.
OutputOnly stdout is returned. Most tools write the JSON report to stdout and progress chatter to stderr. Gitleaks is the exception and writes to a file.
Empty stdoutReturned as-is when the exit code is accepted: gitleaks and npm audit legitimately print nothing when the code is clean, and that is not a failure. Empty stdout with an unaccepted exit code raises ScannerError with the last 500 characters of stderr.
Cleanupcontainer.remove() in a finally, always.

Findings are persisted through _save_finding, which uppercases the severity and stores optional remediation text. ScannerError carries a tool name so the pipeline can tell the operator which scanner broke.

3. Gitleaks (secrets)

backend/app/engine/gitleaks_scanner.py

SettingValue
Imagezricethezav/gitleaks:latest (unpinned)
Commanddetect --no-git --source /src --report-format json --report-path /src/.svs_gitleaks_report.json --no-banner

Gitleaks streams nothing usable to stdout, so the report file is read back from the mount. If the file is absent or empty, the scan is clean and 0 is returned — not an error. The finally block deletes the report file, because it holds matched secrets in cleartext and should not outlive the scan directory. Every leak is normalized to vulnerability type Secret-Leak, severity CRITICAL, remediation "Revoke the secret immediately and rotate it."

4. Dependency audit (SCA)

backend/app/engine/dependency_scanner.py — language is detected from the project root: requirements.txt selects Python, package.json selects JavaScript, and neither means 0 findings.

4.1 Python path

SettingValue
Imagepython:3.11-slim
Commandsh -c "pip install --quiet pip-audit >/dev/null 2>&1 && pip-audit -r requirements.txt --format json"
Mount:/src:ro
NetworkEnabled, to fetch the CVE advisory database

The -r requirements.txt is load-bearing: with no arguments pip-audit audits the container's environment, not the project. Output is walked as dependencies[].vulns[]; each vulnerability becomes a Dependency-Vulnerability finding at HIGH, filed against requirements.txt.

4.2 JavaScript path

SettingValue
Imagenode:18-alpine
Commandsh -c "if [ ! -f package-lock.json ]; then npm install --package-lock-only --ignore-scripts --no-audit --no-fund >/dev/null 2>&1; fi; npm audit --json"
Mount:/src — read-write, so a missing lockfile can be generated
NetworkEnabled, for the registry and the advisory feed

Three details in that command are deliberate and each has caused a failure before:

  • --ignore-scripts means the scanner never executes the target repo's install or postinstall hooks — arbitrary code from untrusted input. It is also what makes repos with workspace-hopping postinstall scripts scannable at all.
  • The separator is ;, not &&, so a failed lockfile generation does not short-circuit the audit.
  • npm audit exits 1 when it finds vulnerabilities, which is why the runner accepts exit code 1.

npm audit reports its own failures (missing lockfile, unreachable registry) as a JSON error object with exit 1 and empty vulnerability data. Without an explicit check that would read as "clean", so the scanner raises ScannerError("SCA Audit", ...) when "error" is present.

V. Findings normalization

FindingNormalizer (backend/app/engine/normalizer.py) is the choke point where three unrelated tool vocabularies collapse into one. Scoring, the findings API, and the PDF all consume that one shape, so a mapping bug would silently poison all three rather than break anything visibly.

The severity maps

SEMGREP_SEVERITY = {"ERROR": "HIGH", "WARNING": "MEDIUM", "INFO": "INFO"}
NPM_SEVERITY     = {"critical": "CRITICAL", "high": "HIGH",
                    "moderate": "MEDIUM", "low": "LOW", "info": "INFO"}
  • Semgrep reports ERROR/WARNING/INFO; SVS scores CRITICAL/HIGH/MEDIUM/LOW/INFO. There is no Semgrep level that maps to CRITICAL.
  • npm reports moderate, not medium. A naive .upper() produced a severity the scoring weights do not recognize, and every moderate advisory silently scored zero and counted toward nothing. The explicit map fixes that.
  • Unknown values fall back to MEDIUM, never to zero, at every level: the normalizer, the scorer's WEIGHTS.get(severity, 4), and the severity counter.

Output shape

Every normalizer returns the same dict, consumed as **kwargs by _save_finding:

FieldSource per tool
v_typeSemgrep: the rule's check_id. Gitleaks: literal Secret-Leak. Both SCA paths: literal Dependency-Vulnerability.
severitySemgrep and npm: mapped as above. Gitleaks and pip-audit: constant CRITICAL and HIGH respectively.
file_pathSemgrep: the affected file. Gitleaks: the file containing the secret. SCA: requirements.txt or package.json.
lineSemgrep: start.line. Gitleaks: StartLine. SCA: 0 — a manifest has no single offending line.
descThe rule message, the rule ID, or the vulnerable package and advisory id.
remediationThe rule's own remediation text, or a fixed string per tool (rotate the secret; update the package; run npm audit fix).
Tool attribution is derived, not stored. The findings API infers the source tool from vulnerability_type: Secret-Leak → Gitleaks, Dependency-Vulnerability → "SCA Audit", anything else → Semgrep (backend/app/api/scans.py:147). This is correct only while the three scanners keep those exact type values; a scanner_tool column would be needed if that changes.

The module ships with an executable self-check (python -m app.engine.normalizer) asserting the severity map, including that a finding with no severity field still lands in a scored bucket.

VI. Scoring

1. Formula and weights

backend/app/engine/scoring.py

WEIGHTS = {"CRITICAL": 10, "HIGH": 7, "MEDIUM": 4, "LOW": 1, "INFO": 0}
DEDUCTION_SCALE = 25.0

risk   = sum(WEIGHTS[f.severity] for f in findings)   # unknown severity -> 4
score  = round(100 / (1 + risk / 25))

Info findings count zero. The scan row stores the score plus the four severity counts, which is what the dashboard aggregates without a join.

3. Why hyperbolic, not flat

A flat 100 - deduction saturates at 0. A repo with 25 medium findings and one with 300 both score 0 and stop ranking anything. The hyperbolic discount keeps 100 for a clean repo, never reaches 0, and stays strictly discriminative at every scale: 40 mediums score 14, 80 mediums score 7, so a worse repo is always a lower number. The documented ceiling is that no score can ever hit 0, only approach it — which is the intended behaviour.

The frontend mirrors this: the dashboard and report view both print score = 100 / (1 + risk/25) and the weight table next to the number, and the report view grades A ≥ 90, B ≥ 80, C ≥ 70, D ≥ 60, F below.

The scoring module has a __main__ self-check using fake query objects that asserts: clean is 100, 40 medium > 80 medium in score, critical < high < low, unknown severity equals medium, and mixed-case severities match uppercase.

VII. API reference

FastAPI, served on http://127.0.0.1:8000. Live Swagger at /docs, OpenAPI at /openapi.json. Every route requires no authentication and applies no ownership filter. Scan-triggering routes are rate-limited.

1. Conventions

  • JSON for /projects bodies; multipart/form-data for the scan routes, because they carry files and form fields together.
  • Errors are FastAPI's {"detail": "..."}; the frontend's client prefers that field and falls back to the status text.
  • GET /scans/ and GET /scans/{id} return different shapes: the list uses critical_count, the detail uses flat critical. The frontend keeps two interfaces for this reason.

3. Migration and startup

Schema creation is deliberately primitive and happens at import time in app/main.py:

  1. Base.metadata.create_all(bind=engine) creates all four tables on a fresh database and is a no-op on an existing one.
  2. Because create_all will not ALTER an existing table, the one schema change since the initial release is applied explicitly and idempotently: ALTER TABLE findings ADD COLUMN IF NOT EXISTS triage_status VARCHAR(16) NOT NULL DEFAULT 'open'.

There is no Alembic. Adding a column means adding a guarded ALTER here.

4. The users table without authentication

Auth was removed because SVS runs on the operator's own laptop and is not exposed publicly. The table survives for the FK and for the historical rows. The resolution function is deterministic: every request in the process's lifetime resolves to the same local user, so new projects get a stable owner and the rate limiter has one key. The UserCreate/UserOut schemas still exist in schemas/user.py but no route uses them.

Documentation drift. The frontend's Architecture Docs → Database Schema (ERD) panel describes a schema that does not exist: UUID primary keys, a role column, JSONB severity counts, a scanner column, and "Prisma ORM". The real schema is the one above. That panel is stale spec text, not a description of the shipped database, and should not be trusted. See section XV.

IX. Frontend

Vite + React 19 + TypeScript, Tailwind CSS v4, lucide-react icons. Five views, one stateful shell, no router library and no global store: navigation is a activeTab string in App.tsx.

1. Application shell and state

frontend/src/App.tsx holds:

  • scans and projects, loaded together in one Promise.all and mapped through the adapter.
  • activeScanId, with activeScan falling back to the first row so the report tab has something to show.
  • A polling effect: while any scan is scanning, a 2500 ms interval re-runs the load. The interval is cleared when nothing is in flight.

Findings are attached to a scan object only when that scan is opened. This keeps the dashboard to two list calls regardless of how many scans exist.

5. What the UI simulates

The stage indicators and terminal log lines are an approximation. The backend reports only PENDING / RUNNING / COMPLETED / FAILED; there is no per-stage status table. The ingest view advances its five stages on a timer while the worker is in flight and snaps to the real state when the status lands. The log lines are static strings describing what each stage does, not streamed tool output. The Branch / Tag / Commit field is advisory only: the backend has no branch column and always clones the default branch at depth 1. Per-stage status would need a stage table in the API.

6. Build and serving

The Dockerfile is a two-stage build: node:20-alpine runs npm install and npm run build, then the dist output is copied into nginx:stable-alpine. VITE_API_URL is a build argument, not a runtime variable, because Vite only exposes VITE_-prefixed vars to the bundle; the API origin is baked into the JavaScript. The compose file passes FRONTEND_API_URL in as that build arg.

nginx.conf has two behaviours worth knowing: static assets get expires 1y with an immutable cache header and a real 404 on a missing file (serving HTML for a missing .js would make the browser run HTML as JavaScript and the app would fail to boot with a syntax error); everything else falls back to index.html for the SPA. The dev server runs on port 3000 with --host=0.0.0.0, which conflicts with the compose frontend, so local development requires stopping the container first.

4. Rate limiting

  • 5 requests per rolling 1-hour window per user, applied to /scans/git, /scans/upload, and /scans/demo only.
  • Implemented with a Redis pipeline: INCR then TTL, and EXPIRE set only when the TTL reads -1 (a key with no expiry), which is the first request of a window.
  • Overrun raises 429 with a message naming the limit. The counter is keyed rate_limit:user_<id>, and because there is one user there is one key.

5. CORS

Origins come from settings.CORS_ORIGINS so a deployment does not need a code change to allow its own domain; an empty list still permits same-origin requests. Compose sets http://localhost:3000,http://127.0.0.1:3000 because CORS compares origin strings and a browser reaching the app via either spelling must be allowed.

XI. Security posture

SVS runs untrusted code analysis on a laptop. Some boundaries are careful and deliberate; some exposures are accepted by the single-user deployment model. Both are listed, because a reader needs to know which is which.

1. Deliberate boundaries

  • Least-egress containers. Every scanner runs in its own container with a memory cap (256–512 MB) and a 15-minute timeout. Gitleaks runs with no network at all; Semgrep and the CVE audit egress only to fetch the ruleset and the advisory database.
  • Read-only mounts where possible. Semgrep and pip-audit mount /src:ro. Only Gitleaks and npm mount read-write, and only because they must write a report or generate a lockfile.
  • No execution of target code during install. --ignore-scripts on every npm invocation means the scanner never runs the target repo's install or postinstall hooks — arbitrary code from untrusted input.
  • SSRF validation server-side. Scheme allowlist, netloc required, hostname resolved, and every resolved address rejected if private, loopback, link-local, multicast, or reserved. Unresolvable hostnames and unparseable addresses are rejected, not passed through. Cloud metadata (169.254.169.254) is covered by the link-local rule.
  • SSRF guard client-side. The Git URL field rejects localhost, RFC 1918 ranges, the metadata endpoint, and file:// / gopher:// before the request is made, with an inline warning.
  • Size ceiling. 50 MB on uploads, enforced in the frontend, the ingestion service, and the multipart body.
  • Ephemeral storage. The scan directory is rmtree'd in a finally on success and failure. The Gitleaks report, which contains matched secrets in cleartext, is deleted separately before that.
  • Scanned code never leaves the host. Only the ruleset and the advisory database traverse the network.
  • Rate limiting. 5 scans per hour per user.

2. Honest exposures

These are real. They are accepted by the deployment model, not mitigated.
  • The Docker socket is mounted into the backend and worker containers. Anything that can reach the API can start arbitrary containers on the host with arbitrary mounts. This is how the scanners work; it is also full host compromise if the API is exposed.
  • No authentication. There is no token, session, or ownership check anywhere. If port 8000 is reachable, it is fully usable.
  • PostgreSQL is published on 5432 with the credentials in .env (svs_password), which are the same ones used for local development and are not secret in any meaningful sense.
  • The SECRET_KEY in .env is a leftover from the removed JWT authentication and is read by nothing.
  • Scanner images are unpinned (semgrep/semgrep, zricethezav/gitleaks:latest, node:18-alpine). A hostile or compromised upstream tag would run inside the sandbox. Only python:3.11-slim and the Postgres/Redis images are version-anchored by the compose file.
  • Zip extraction is not path-traversal hardened. ZipFile.extractall honours absolute and .. paths in recent Python, but a hostile archive is still the threat model this scanner is built to analyze, so treat untrusted zips as untrusted input.

The conclusion to write down: SVS is safe to run on your own laptop against code you already have, and unsafe to expose on a network.

3. SSRF controls, client and server

The two checks are independent and both run. The client's regex list rejects obvious internal spellings and gives immediate feedback; the server's DNS-resolution check is the one that actually matters, because it catches a hostname that resolves to an internal address regardless of how it is spelled. A public hostname with an internal A record is caught server-side and silently passes the client.

XIII. Operations

1. run-svs.bat step by step

  1. Checks the Docker daemon. If it is not up, starts Docker Desktop and polls docker info once a second for up to ~90 seconds. Without this the build fails with a confusing "daemon not running" npipe error.
  2. Builds the three images — docker compose build backend worker frontend. Code is baked into the images, not bind-mounted, so this is how edits take effect. It costs seconds when nothing changed, because of layer caching.
  3. Starts the stack — docker compose up -d.
  4. Waits for the API health probe — curls http://127.0.0.1:8000/health every 2 seconds, up to 60 tries, because the backend runs the schema migration on boot. A timeout warns but continues.
  5. Opens the browser at http://127.0.0.1:3000 and prints the URL table and the stop/log commands.

start.bat is the bare version: docker compose up -d --build, a 10-second wait, and the same browser open. Use it when Docker is already running and the health probe is not needed.

2. The localhost shadow on port 3000

Use 127.0.0.1, not localhost. A VS Code PHP server already owns [::1]:3000 on this machine, so localhost:3000 resolves to that mock application instead of SVS. The launcher, the browser open, and the README all spell the address explicitly for this reason. This is an environment quirk of this laptop, not a property of the application.

3. Editing code: rebuild is mandatory

Backend and frontend code is copied into the images at build time. There is no volume mount of the source. Any edit to backend/ or frontend/ requires docker compose build backend worker frontend before up -d — which is exactly what run-svs.bat does. A plain docker compose up -d after an edit silently runs the old code. The only runtime-mounted paths are the Docker socket and /tmp/svs_uploads.

For frontend hot reload instead, stop the compose frontend first (port conflict), then cd frontend && npm install && npm run dev, which serves on http://127.0.0.1:3000 and talks to the API at VITE_API_URL.

XV. Known limitations and documentation drift

Read this section before trusting anything that looks like it documents itself.

Functional limitations

  • No per-stage status. The API reports four states. The ingest view's five stage indicators and its terminal log are a timed approximation, not real progress.
  • The branch field does nothing. Repo.clone_from(..., depth=1) takes no branch argument; the default branch is always what is scanned.
  • No code snippets, CWE, or CVE columns. The findings table has no place for them, and the scanned tree is deleted at the end of the scan, so the offending line is gone by the time anyone reads the report. The UI shows the file and line and explains the absence.
  • No ownership or multi-tenancy. Every project and scan belongs to the one local user; there is no way to partition data.
  • Triage vocabulary is closed. Four values; anything else is a 400.
  • Dependent on the host Docker daemon. If it is unreachable, scans fail with a plain FAILED and no scanner detail.
  • Archive handling is asymmetric. The UI advertises .tar.gz; the API accepts only .zip.

Documentation drift

The in-app "Database Schema (ERD)" panel is wrong about the shipped schema. ArchitectureDocsView.tsx, "Database Schema (ERD)" sub-tab, describes UUID primary keys, a role column on users, JSONB severity counts, a scanner column on findings, a user_id FK, and "Prisma ORM". None of that exists. The real schema is in section VIII. Do not edit code against that panel.
  • The "15-Step AI Implementation Prompts" panel is the original build spec, written before the code existed. It is accurate as provenance — it is the prompt series that produced this system — but it describes an intended system, including an authentication and tenant-isolation step that was later deliberately removed.
  • The frontend navbar reads v2.4 and the package.json reads "version": "0.0.0". Neither is tracked or released; the badge is decorative.
  • The API reference panel duplicates the real routes and is currently accurate, but it is static data in docsAndPrompts.ts, not generated from the live OpenAPI. Prefer http://127.0.0.1:8000/docs.
  • The "Download Full Project ZIP" link points at /svs-security-scanner-project.zip, which nginx does not serve; it 404s.
  • frontend-cra-legacy/ is the superseded Create React App build. It has its own Dockerfile and nginx config and is not referenced by the compose file. It is kept for reference only.
